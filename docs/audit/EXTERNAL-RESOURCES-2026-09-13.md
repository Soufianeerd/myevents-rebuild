## Hanna — primitives de mise en scène

Sources : [dépôt](https://github.com/Soufianeerd/hanna), [production](https://hannasalma.netlify.app/). Copie de lecture hors du projet, sans npm install. Vite vanilla + GSAP ; configuration assets/géométrie/motion/audio séparée, `HannaExperience`, `EnvelopeScene`, modules d'animation et service RSVP.

Le code actuel commence par un geste explicite de découverte, puis arrivée/flottement, rotation 3D, ouverture du sceau, enveloppe ouverte, extraction/présentation, carte et formulaire. L'ouverture et la carte finale ont été inspectées sur Chromium mobile. Le verrou `hasOpened` et les gardes sur l'état évitent les doubles ouvertures. Les timelines et listeners disposent de méthodes de nettoyage ; leur exhaustivité reste à vérifier avant toute réutilisation conceptuelle dans React.

Le state manager est un registre avec abonnements, **pas une machine qui valide elle-même un graphe de transitions**. Le README n'est pas entièrement à jour : il décrit notamment un RSVP par code invité et un arrêt musical à CARD_READY, tandis que le service actuel envoie prénom/nom/email/présence à Apps Script et que l'orchestrateur conserve la musique jusqu'à l'envol. Le calcul mobile actuel de carte privilégie une largeur native et le scroll, pas une garantie universelle « tout tient sans scroll ». Ne pas transformer ces anciennes promesses en critères MyEvents.

| Concept observé                    | Abstraction MyEvents proposée                         | Contraintes                                                                                    |
| ---------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Images avant/arrière/poche/carte   | EnvelopePreset + AssetRef + GeometryPreset            | Ratios/anchors déclaratifs ; aucune dimension de Hanna imposée à tous les templates            |
| Geste d'entrée                     | InteractionTrigger / start gate                       | Bouton sémantique, clavier, double tap, option sans son                                        |
| Arrivée/idle/flip/sceau/extraction | OpeningExperience + AnimationTimeline + CardReveal    | Graphe de transitions contrôlé, annulation/skip, reduced motion                                |
| Continuité de pose                 | Pose/transform calculée depuis géométrie              | Ne pas déplacer arbitrairement le DOM au milieu de la transition                               |
| Musique                            | AudioTrack + AudioPolicy                              | Geste utilisateur synchrone, mute, indisponibilité, fade, cleanup ; tester Safari réel         |
| Fenêtre mobile                     | ViewportAdapter + safe areas + responsive constraints | VisualViewport/resize/orientation/clavier ; ne pas prendre un viewport Chromium pour un iPhone |
| Réponse puis envol                 | RSVP state + completion effect                        | Confirmer uniquement après persistance serveur ; distinguer erreur, envoi et succès            |

**À apprendre :** progression tactile lisible, peu de commandes, rendu physique convaincant, son facultatif, qualité de la transition jusqu'au contenu.

**À améliorer :** texte sémantique éditable au-dessus d'un décor plutôt qu'une carte raster monolithique ; state machine testable, liens privés contrôlés, reprise réseau, animation pilotée par données. L'audit externe n'a soumis aucune réponse et n'a donc pas validé le backend ni le post-RSVP en production.

## Invitation Salma & Soufiane — composition et continuité

Sources : [dépôt](https://github.com/Soufianeerd/invitationmariagesalmaetsoufiane), [production](https://invitationmariagesalmaetsoufiane.netlify.app/).

La version racine observée utilise HTML/CSS/JS, une ouverture par sceau et portes, des timers CSS/JS et IntersectionObserver pour les révélations. Ne pas affirmer que toutes les animations de ce dépôt utilisent GSAP. Plusieurs copies de l'invitation et micro-applications audio/photo coexistent ; c'est une référence d'expérience, pas une structure à importer dans MyEvents.

L'ouverture, le hero et le formulaire ont été vus dans le navigateur. La composition crème/bordeaux, noms de familles, prénoms, passage arabe avec traduction, programme de deux lieux, itinéraires et calendrier donnent une progression éditoriale cohérente. Le sceau d'ouverture est une image cliquable dans le code actuel, à remplacer conceptuellement par un contrôle clavier accessible. La date limite RSVP affichée (1er septembre 2026) est déjà passée au jour de l'audit : c'est du contenu daté, pas une règle à copier.

Primitives à représenter dans le même document : Hero, FamilyNames/CoupleNames, RichText avec `lang`/`dir`, Quote/ReligiousText configurable, Program/Timeline, Location/MapLink, Countdown, CalendarCTA, RSVPFormRef, GalleryRef, AudioGuestbookRef, Footer. Données culturelles et textes restent des données ; aucun moteur par type de mariage.

L'audio et les photos ont des micro-applications et scripts Apps Script/Drive/Sheets dans le dépôt. La page publique principale ne démontre pas à elle seule un funnel intégré audio/photo et droits d'accès. L'URL calendrier est présente ; son téléchargement et sa validité doivent être contrôlés avant de retenir le comportement comme preuve fonctionnelle.

**À apprendre :** hiérarchie des informations, continuité invitation → réponse → souvenirs, sections réordonnables et liens pratiques immédiatement compréhensibles.

**À améliorer :** contenu versionné, contrôle des droits, textes réellement accessibles, gestion des erreurs, timezone explicite, durée d'ouverture réglable, un seul renderer et un seul modèle plutôt que des copies HTML.

## Studio : décision d'architecture proposée

Garder le DOM/CSS responsive comme représentation de l'invitation. Un canvas bitmap global complique le texte, le RTL, les formulaires RSVP, l'accessibilité et l'adaptation mobile. Réserver une éventuelle surface 2D aux manipulations qui le nécessitent, notamment le print ; conserver un modèle document commun et un export dédié.

1. **Document versionné** : metadata, theme, background, openingExperience, soundtrack, sections/elements identifiés, animations, responsive, interactionRules ; schémas Zod et migrations explicites.
2. **Registry de blocs** : schéma de contenu/propriétés, renderer, inspector et contraintes par type. Children typés pour sections imbriquées, ordre stocké par IDs ; modèles/presets = données.
3. **État éditeur séparé** : sélection, hover, calques, arbre, panneau inspecteur, zoom et mode Express/Personnalisation/Avancé. Aucun état transitoire dans le snapshot public.
4. **Commandes métier** : ajouter/supprimer/dupliquer/déplacer/modifier ; historique undo/redo par transaction utilisateur ; regrouper un drag en une opération. Autosave avec révision attendue et conflit explicite ; snapshot publié immuable.
5. **Mise en page contrainte** : grilles/anchors, tailles bornées, propriétés logiques, héritage thème → bloc → override de breakpoint. Resize/rotation/snapping limités aux blocs compatibles. DnD clavier et boutons de déplacement alternatifs.
6. **Animations déclaratives** : trigger, target IDs, durée/délai/easing/stagger/répétition, fallback reduced motion ; compilation par AnimationAdapter. Aucun JS libre provenant du document. Montage/démontage, changement de template et replay doivent nettoyer les effets.
7. **Assets** : IDs de médias et métadonnées de dimensions/droits/taille ; pas d'URLs arbitraires privilégiées ni duplication du fichier par bloc. Preview et public utilisent le même renderer.

### GSAP : point de décision avant adoption

[GSAP Standard License](https://gsap.com/community/standard-license/) renvoie aux [conditions Webflow, section GSAP](https://webflow.com/legal/product-terms). La disponibilité gratuite de plugins ne signifie pas une licence MIT : les conditions limitent certains usages d'éditeurs visuels d'animation concurrents. Le Studio avancé MyEvents pouvant exposer une interface de création d'animations, **la compatibilité exacte de cet usage reste à clarifier**. Ce rapport ne tranche pas juridiquement son applicabilité.

Core/timelines servent aux ouvertures et transitions ; ScrollTrigger aux révélations ; Flip aux changements de disposition ; Draggable éventuellement à un contrôle spécialisé ; SplitText impose en plus des contrôles de texte/RTL/accessibilité. Ne pas adopter toute la suite par défaut. `@gsap/react` apporte nettoyage/context React, mais ne remplace pas le modèle document. Évaluer CSS/Web Animations derrière AnimationAdapter pour garder le modèle indépendant si la licence GSAP ne convient pas.

## Installations réellement utiles proposées après diagnostic

1. **Tout de suite pour fiabiliser les preuves :** aucune dépendance produit supplémentaire ; rendre le runtime/check reproductible, puis installer le moteur WebKit de la version Playwright déjà verrouillée. Pas besoin de remplacer Next, React, Zod ou Radix.
2. **Lors de la session adapters R3 :** SDKs officiels Supabase/Stripe et un seul provider mail ; MCP Supabase facultatif, limité au projet de développement. Aucun besoin de Stripe Connect pour vendre les propres produits MyEvents à ce stade.
3. **Lors du Studio :** petite évaluation Puck vs registry interne + dnd-kit ; ne pas installer plusieurs éditeurs. GSAP conditionné au résultat de la vérification de licence pour l'usage proposé.
4. **Skills locaux :** le contrat existant couvre déjà produit/architecture. Préférer ultérieurement un skill `myevents-release` (gates, données/ports isolés, preuves) et un `myevents-studio` (document/renderer/responsive/animations), quand R0/R2 auront stabilisé les conventions. Ne pas créer vingt skills qui recopient les docs. Product-marketing/CRO peuvent être adaptés lors de R6.

Aucune installation n'a été effectuée pendant la recherche. La priorité reste de rendre le parcours réel testable puis vendable, pas d'augmenter le nombre de plugins.
